# AgentNotify — разовые напоминания Windows из OpenCode

Агент в OpenCode разбирает естественный язык и ставит **разовое** напоминание. Дальше всё
делает Windows: точный триггер Планировщика заданий показывает нативный toast по сроку, даже
если OpenCode закрыт. Модель при доставке не участвует, текст напоминания нигде не исполняется.

В репозитории только исходники: готовых сборок здесь нет, всё собирается локально из этого
дерева. Инструкция для агента другого харнесса (сборка, подключение MCP, контракты инструментов,
диагностика и откат) — в [`docs/harness-integration.md`](docs/harness-integration.md); правила
поведения агента при работе с напоминаниями — в [`AGENTS.md`](AGENTS.md).

## Состав

| Компонент | Что делает |
|---|---|
| `src/AgentNotify` | CLI + воркер + MCP-сервер stdio в одном exe (`schedule`, `list`, `update`, `cancel`, `run-due`, `install`, `uninstall`, `status`, `context`, `serve-mcp`) |
| `src/AgentNotify.Launcher` | оконно-невидимый лаунчер (`WinExe`) для Планировщика: запускает `AgentNotify.exe` с `CreateNoWindow` и передаёт его код выхода |
| SQLite `%LOCALAPPDATA%\AgentNotification\reminders.db` | постоянная очередь: `pending → sending → sent` или `cancelled` |
| Планировщик заданий Windows | на каждое напоминание — точный `TimeTrigger`; одна задача-обход `...Sweep` (при входе + каждые 5 минут) |
| Toast | `Microsoft.Toolkit.Uwp.Notifications`, AUMID привязан к пути exe |
| `tests/AgentNotify.Tests` | xunit-тесты очереди, валидации, XML задач, отмены, миграции задач, лаунчера, MCP |
| `tests/mcp-wire-test.mjs` | wire-проверка MCP через реальный процесс (initialize / tools/list / tools/call) |

Требования: Windows 10/11 x64, .NET 8 runtime (SDK достаточен), сеть для `dotnet restore`.
Никаких глобальных установок, служб и повышения прав не требуется.

## Установка

```powershell
cd <путь к клонированному репозиторию>
pwsh -File scripts\build.ps1            # publish в %LOCALAPPDATA%\AgentNotification\app + регистрация обхода
```

`scripts\build.ps1 -SkipInstall` — только публикация. Публикация в стабильный каталог важна:
AUMID toast вычисляется из пути exe, при переносе exe настройки уведомлений Windows не подхватятся.
В каталог публикуются **два** exe: `AgentNotify.exe` (CLI, воркер, MCP) и `AgentNotify.Launcher.exe`
(оконно-невидимый запуск задач Планировщика). Вручную второй exe запускать не нужно.

`scripts\build.ps1 -Target <каталог>` — сборка в отдельный каталог (staging). В этом режиме
`install` не выполняется, задачи и live-каталог не меняются.

### Обновление уже установленной сборки

```powershell
# 1) закрыть/отключить MCP-клиенты, которые держат AgentNotify.dll (иначе publish не перезапишет файл)
# 2) одной командой: publish обоих exe + регистрация обхода + миграция существующих задач
cd <путь к клонированному репозиторию>
pwsh -File scripts\build.ps1
& "$env:LOCALAPPDATA\AgentNotification\app\AgentNotify.exe" status --json
```

`install` внутри `build.ps1` делает всё нужное: перерегистрирует обход на лаунчер, переводит
уже поставленные напоминания на лаунчер (`migrated`) и восстанавливает пропавшие триггеры.
Данные и сроки не меняются, чужие задачи не затрагиваются.

Проектный MCP уже описан в `opencode.json` (`mcp.servers.agent-notification`, local stdio).
Перезапуск сервиса OpenCode не нужен: конфиг проектный и применяется в этом каталоге. Проверка
для **этого проекта** (обычный `opencode mcp list` без `location[directory]` смотрит другую
область и может показать «No MCP servers configured»):

```powershell
opencode api mcp.list --param 'location[directory]=<путь к репозиторию>'
```

Ожидается `agent-notification: connected`; агент видит четыре инструмента
`agent_notification_schedule_reminder`, `..._list_reminders`, `..._update_reminder`,
`..._cancel_reminder` (в Code Mode — `tools.agent_notification.*`).

## Оконно-невидимый запуск (почему нет окна терминала)

`AgentNotify.exe` — консольное приложение. Если Планировщик запускает его напрямую, Windows
создаёт окно консоли, и оно на мгновение выходит на передний план перед toast. Поэтому задачи
запускают `AgentNotify.Launcher.exe`:

- лаунчер собран как `WinExe` (GUI-подсистема), поэтому Планировщик не создаёт для него консоль;
- он запускает соседний `AgentNotify.exe` с `CreateNoWindow=true`, `UseShellExecute=false` и
  перенаправленным выводом, ждёт завершения и возвращает его код выхода;
- контракт узкий: только `run-due [--home <путь>]`. Любая другая команда или лишний аргумент
  отклоняется (код 2). Лаунчер не является исполнителем произвольных команд и не принимает путь
  к запускаемому exe из аргументов;
- путь `AgentNotify.exe`, AUMID toast, настройки Windows, история уведомлений, CLI и MCP не меняются:
  основной процесс остаётся тем же файлом.

Коды выхода лаунчера: `0`/`4` — как у дочернего процесса (`run-due`), `2` — нарушен контракт
аргументов, `5` — рядом нет `AgentNotify.exe`, `6` — дочерний процесс не завершился за 9 минут,
`7` — не удалось запустить. Диагностика пишется в `worker.log` только при ошибке.

### Миграция уже поставленных задач

Задачи, созданные прежней сборкой, указывают на консольный exe. `install` (и `repair`) читают
фактический `Action/Command` каждой будущей задачи и перерегистрируют только те, где команда
отличается:

```powershell
& $exe install --json    # sweep + миграция + ремонт: migrated / retiredOverdueTriggers / blockedOverdueTriggers / migrationAlreadyOk / migrationFailed / migrationRemaining
& $exe repair --json     # только миграция и ремонт, без перерегистрации обхода
& $exe status --json     # sweepCommand, sweepUsesLauncher, launcherPresent
```

- срок берётся из очереди, поэтому `StartBoundary` после миграции совпадает с прежним;
- `Principals/Principal` не меняется: остаётся `InteractiveToken`, `LeastPrivilege`, тот же `UserId`;
- очередь читается постранично (страницы по 100 записей, keyset-курсор по сроку и id), без общего
  лимита `list` в 500; за проход выполняется до 500 реальных перерегистраций
  (`MigrationBatchLimit`), лимит считают только они;
- если очередь больше, `migrationRemaining > 0` считается по фактическому остатку очереди, а
  отметка о завершении не пишется — то есть хвост очереди не может остаться незамеченным;
- **просроченные записи** (`due` уже прошёл) обрабатываются отдельно: их точный триггер указывает
  на консольный exe и мог бы сработать с окном при следующем входе или выходе из сна. Если задача
  обхода уже запускает лаунчер (невидима), собственный legacy-триггер такой записи **снимается**
  (`retiredOverdueTriggers`), сама запись остаётся в SQLite `pending`, и её доставляет обход.
  Если обход ещё не подтверждён как невидимый (нет задачи обхода или она запускает консольный exe),
  триггер не снимается (`blockedOverdueTriggers`), миграция не считается завершённой и повторяется
  следующим обходом: единственный путь доставки не удаляется;
- `sending` записи не трогаются: их уже доставляет другой обработчик;
- отметка о выполненной миграции хранится в `%LOCALAPPDATA%\AgentNotification\task-command.txt`
  (рядом с базой). Пока отметка не совпадает с текущей командой, обход `run-due` при каждом
  запуске продолжает миграцию с остатка — установку не нужно повторять вручную;
- ошибки перерегистрации не теряют запись: остаётся `pending` с `last_error`, `migrationFailed > 0`,
  и обход повторит попытку.

**Честное узкое окно.** Пока новый лаунчер не опубликован и `install` не отработал, задачи
запускают консольный exe, и окно может появиться (сюда же попадает момент, когда старая задача
уже стартовала). Поэтому обновление делается одной командой `pwsh -File scripts\build.ps1`
(publish → install сразу). После успешного `install` (и при `usesLauncher: true` в ответе) новых
окон нет. Если задача стояла на момент миграции, её `StartBoundary` мог уже пройти — она сработает
сразу после перерегистрации, но уже через лаунчер, то есть без окна; дубля показа не будет
(claim в очереди).

**Сборка без лаунчера.** Если рядом с `AgentNotify.exe` нет `AgentNotify.Launcher.exe`, задачи
регистрируются на консольный exe, но это не молчит: `schedule`/`install` возвращают предупреждение
«может показать окно терминала», `status` пишет, что лаунчер не найден (`launcherPresent: false`),
а `sweepUsesLauncher` показывает фактическое состояние задачи обхода.

## Откат

```powershell
pwsh -File scripts\uninstall.ps1                 # удалить задачи обхода и напоминаний этого пользователя
pwsh -File scripts\uninstall.ps1 -PurgeData      # плюс удалить reminders.db и журнал (безвозвратно)
```

Вручную: `AgentNotify.exe uninstall`, затем при желании удалить
`%LOCALAPPDATA%\AgentNotification\app`. Задачи удаляются только с именами `AgentNotify.<hash SID>...`;
чужие задачи не затрагиваются. Следы toast — `AgentNotify.exe test-clear-history` и обычная
очистка Центра уведомлений.

## Ежедневное использование

```powershell
$exe = "$env:LOCALAPPDATA\AgentNotification\app\AgentNotify.exe"
& $exe context --json
& $exe schedule --at "2026-11-27T09:30:00+03:00" --text "Позвонить в сервис"
& $exe list --all --json
& $exe update rem_0123456789abcdef --at "2026-11-27T11:45:00+03:00"
& $exe update rem_0123456789abcdef --text "Новый текст"
& $exe cancel rem_0123456789abcdef
& $exe status --json
```

Через агента: «напомни завтра в 9:30 позвонить в сервис». Агент обязан вызвать `list_reminders`
для локального времени и зоны, уточнить неоднозначность и подтвердить успех только при
`windowsTaskRegistered: true` (правила — в `AGENTS.md`).

## Поиск активных напоминаний

Поиск — это тот же `list_reminders` с необязательными фильтрами. Без аргументов поведение
прежнее: активные `pending/sending` (до 500), `timeContext`, `sweepTaskRegistered`, `counts`.
Критерии объединяются по **AND**, поиск ничего не меняет в очереди и не выполняет текст записей.

| Аргумент | Смысл |
|---|---|
| `text` | Литеральная подстрока текста без учёта регистра Unicode (`OrdinalIgnoreCase`); без морфологии: «оплат» найдёт «оплата» и «оплатить», «оплата» не найдёт «оплатить». |
| `from` | Нижняя граница срока **включительно**, ISO 8601 с явным смещением (сравнение по UTC). |
| `to` | Верхняя граница срока **исключительно**, ISO 8601 с явным смещением. |
| `overdue` | `true` — только записи, у которых срок уже наступил (`due <=` текущего времени). |
| `id` | Точный идентификатор `rem_...`. |
| `limit` | Размер страницы 1..500, по умолчанию 500. |
| `cursor` | `nextCursor` из предыдущего ответа; передавайте с теми же фильтрами. |

Ответ содержит прежние поля и добавляет `returned`, `total` (все совпадения), `truncated`,
`nextCursor`, `appliedFilters`. Если `truncated=true`, совпадения за пределом страницы не
потеряны: следующая страница берётся по `nextCursor`. Порядок устойчивый — по сроку, затем по id.

Время в записи: `dueLocal` — срок в смещении, с которым запись создана (исторический контракт,
не обязательно зона ПК); `dueCurrentZoneLocal` — тот же момент в текущей зоне Windows с учётом
DST на дату срока; `dueUtc` — абсолютный момент. Дробные `from`/`to` округляются **вверх** до
миллисекунды, что сохраняет точный отбор записей с миллисекундной точностью. `total` относится к
моменту ответа: между запросами страниц статус записи может измениться, `nextCursor` не
фиксирует снимок очереди.

Примеры для агента (границы считаются в зоне из `timeContext`, а смещение — для конкретной
даты границы: если она в другом сезоне, DST может отличаться; при неоднозначном или
несуществующем местном времени уточняйте, не угадывайте):

- «Что сегодня осталось» → `from` = 00:00 сегодня, `to` = ближайшая полночь (включая просроченные
  записи этого дня).
- «Напоминания про оплату на этой неделе» → `text: "оплат"`, `from` = 00:00 понедельника,
  `to` = 00:00 следующего понедельника.
- «Какие просрочены» → `overdue: true`.
- «Что с записью rem_...» → `id`.

Вручную через CLI:

```powershell
& $exe list --json --text "оплат"
& $exe list --json --from "2026-11-26T00:00:00+03:00" --to "2026-11-27T00:00:00+03:00"
& $exe list --json --overdue
& $exe list --json --limit 200 --cursor "<nextCursor>"
& $exe list --json --all            # история, фильтры с --all несовместимы
```

## Изменение активного напоминания

`update_reminder(id, at?, text?)` (CLI: `update <id> [--at ...] [--text ...] [--json]`) меняет
текст, будущий срок или оба поля **одной активной** записи `pending`. Нужно передать хотя бы
одно из полей; непереданные поля и `id` сохраняются. Изменять можно только будущую запись
`pending`: `sending`, `sent` и `cancelled` отклоняются без изменения данных.

- Текстовая правка не сдвигает срок и не трогает задачу Планировщика.
- Перенос срока перерегистрирует задачу Windows под **прежним именем** (`...Reminder.<id>`),
  поэтому дубликатов не появляется. Запись нового срока и маркер необходимой перерегистрации
  фиксируются одной транзакцией SQLite (`sync_due_ms`), затем регистрируется триггер.
- Повтор с теми же значениями идемпотентен: `changed=false`, ничего не меняется.
- Если Планировщик отказал или не ответил, изменение **уже сохранено** в очереди и возвращается
  честный частичный статус: `syncPending=true`, `windowsTaskRegistered=false`, предупреждение.
  Обход (или следующая правка) повторит перерегистрацию под тем же именем, даже если старое
  задание ещё существует. Доставка идёт по сроку из SQLite, поэтому старый триггер не отправит
  напоминание раньше нового срока.

Поля ответа: `id`, `text`, `dueLocal`, `dueCurrentZoneLocal`, `dueUtc`, `offset`, `state`,
`changed`, `textChanged`, `dueChanged`, `windowsTaskRegistered`, `windowsTaskName`,
`syncPending`, `sweepTaskRegistered`, `warnings`, `timeContext`. CLI-коды: `0` — успех или
идемпотентный повтор, `1` — запись не найдена или не может быть изменена, `2` — ошибка ввода,
`3` — изменение сохранено, но триггер ещё не подтверждён (`syncPending`).

Как выбирать запись: сначала `list_reminders` (по `id` или фрагменту текста). При точном `id`
работайте с ним; при нескольких совпадениях и без однозначного признака — уточните, не выбирайте
первую. «На час позже» и «на день позже» считаются от прежнего срока записи, «на завтра» — это
завтрашняя дата относительно `nowLocal`/`timeContext` с сохранением часа записи (смещение берётся
для новой даты); при неоднозначности (прошедшее время, разные даты, переход DST) — уточнение.
Создавать или отменять запись вместо изменения нельзя.

Поля `at` и `text` необязательны, но нужно хотя бы одно. Чтобы сохранить поле, его не передают:
явный JSON `null` отклоняется, явно пустой `at` — ошибка. Текстовая правка не регистрирует задачу
Планировщика; если у записи остался маркер незавершённой синхронизации от прошлого переноса, его
снимет обход, а не эта правка.

## Как устроена надёжность

- **Точный срок.** На каждое напоминание регистрируется отдельная задача `TimeTrigger` с
  `StartWhenAvailable=true`, `IgnoreNew`, `DisallowStartIfOnBatteries=false`. Граница округляется
  **вверх** до секунды и переводится в локальную зону машины, поэтому задача не срабатывает раньше
  срока; если момент попал в несуществующее местное время (переход на летнее время), граница
  сдвигается вперёд.
- **Догон.** Задача `...Sweep` запускается при входе в Windows и каждые 5 минут, забирает все
  просроченные `pending` записи и показывает их. Это не точное расписание, а страховка: после сна
  без перелогина задержка до ~5 минут, после выхода из системы — доставка при следующем входе.
  Если задача обхода не установлена (`install`) или недоступна, догона нет — это видно по
  `sweepTaskRegistered` в ответе MCP и в `status`.
- **Конкуренция.** Запись забирается атомарно (`BEGIN IMMEDIATE` + `UPDATE ... WHERE state='pending'`
  с claim-token), `MultipleInstancesPolicy=IgnoreNew` не даёт запускать второй обход. Пересечение
  запусков не создаёт обычного дубля. Изменение (`update_reminder`) идёт в той же дисциплине:
  проверка `pending` и запись — одна транзакция, поэтому конкурентные доставка/отмена либо
  происходят раньше (изменение честно отклоняется), либо видят уже новые данные.
- **Сериализация задания.** Все изменения задачи Планировщика для одной записи (перенос срока,
  восстановление обходом, миграция) идут под общим guard по ID: внутрипроцессный `Monitor` плюс
  именованный `Mutex` для процессов одной сессии. Внутри guard запись перечитывается из SQLite,
  после регистрации маркер снимается условно (только при совпадении срока и `pending`), поэтому
  поздно завершившаяся регистрация старого срока не объявляется успехом и не стирает маркер
  нового. Если именованный `Mutex` недоступен, guard работает fail-closed: регистрация/удаление
  откладываются, а запись остаётся «грязной» для повтора. Обход сначала берёт приоритетную
  очередь «грязных» записей по сроку (по всей базе, а не из первых 500), ожидание guard в фоне
  короткое (2 с), попытки ограничены бюджетом прохода.
- **Схема.** Новые колонки (`updated_utc_ms`, `sync_due_ms`) добавляются аддитивно при открытии
  базы в одной транзакции `BEGIN IMMEDIATE`: параллельные запуски на базе прежней версии не
  конфликтуют, очередь не обязана быть пустой, существующие записи не переписываются.
- **Ошибка отправки.** `Show()` не принят → запись возвращается в `pending` с `last_error`, попытки
  не теряются и повторяются обходом (каждые ~5 минут, пока не будет принято).
- **Зависшая отправка.** `sending` старше 10 минут возвращается в очередь.
- **Уборка задач.** После успешной доставки одноразовая задача удаляется, чтобы Планировщик не
  копил исторические задачи. Пропавшие задачи будущих записей перерегистрируются обходом.
- **Окно терминала.** Задачи запускают `AgentNotify.Launcher.exe` (GUI-подсистема), а он —
  консольный `AgentNotify.exe` с `CreateNoWindow`, поэтому окно не создаётся. Прямой запуск exe
  из Планировщика (старая задача) окно показывал; см. раздел про миграцию.
- **Изоляция пользователей.** Имя каждой задачи — `AgentNotify.<hash SID>.<Sweep|Reminder.id>` (для
  тестовых хранилищ добавляется хэш пути), поэтому две учётные записи Windows не перезаписывают
  задачи друг друга через общий корень Task Scheduler.

## Пределы и честные ограничения

- **Нет exactly-once.** Между фиксацией в SQLite и показом toast нет общей транзакции: при аварии
  ровно между вызовом `Show()` и записью `sent` возможен повторный баннер. Гарантия — «как минимум
  один раз», запись при этом не теряется.
- **«Отправлено» ≠ «увидено».** Успех означает, что Windows принял уведомление (и, как правило,
  запись есть в истории уведомлений). Баннер может быть скрыт: «Не беспокоить»/Focus Assist,
  отключённые уведомления приложения, полноэкранный режим, выключенный экран. Проверить факт
  взгляда невозможно.
- **Показ требует активного сеанса.** Toast — интерактивное уведомление. При **блокировке
  экрана** (Win+L) сеанс остаётся активным: запись может быть доставлена, но баннер на экране
  блокировки не показывается — он появится в Центре уведомлений после разблокировки. При
  **выходе из системы или выключении** сеанс завершается: задачи с интерактивным токеном не
  выполняются, записи ждут и доставляются при следующем входе. Пробуждения из сна нет
  (`WakeToRun=false`).
- **Батарея.** Задачи не блокируются на батарее (`DisallowStartIfOnBatteries=false`), но Windows
  может отложить запуск в энергосбережении; обход догонит позже.
- **Точность.** Триггер не раньше срока; фактическая задержка зависит от Планировщика (обычно
  секунды). Доли секунды округляются вверх до секунды.
- **Смена часового пояса/DST.** Задача хранит локальную границу. При смене зоны или переходе на
  летнее время триггер может сработать раньше/позже; раньше срока запись не доставляется (claim
  проверяет `due_utc`), а обход и перерегистрация восстанавливают расписание **с задержкой до
  интервала обхода**, не мгновенно. Абсолютной точности после смены зоны не гарантируем.
- **Отказ точной регистрации.** Запись остаётся в очереди, но доставка не гарантируется:
  `windowsTaskRegistered=false`, а `sweepTaskRegistered` показывает, найдена ли задача обхода.
  Если её нет, доставка не произойдёт, пока обход не установлен (`install`).
- **Одна учётная запись.** Данные и задачи привязаны к текущему пользователю; другой пользователь
  Windows увидит свою пустую очередь.
- **Повторов нет.** Повторяющиеся напоминания не поддерживаются.
- **Хранилище.** Очередь растёт: завершённые записи остаются для аудита. Вывод `list`/`list_reminders`
  без фильтров ограничен 500 записями за страницу, но усечение теперь явное (`truncated`/`nextCursor`)
  и остаток доступен следующей страницей; очистка — `cancel --purge` для активной и `purge <id>`
  для доставленной/отменённой записи, либо `uninstall --purge-data`.

## Ручные проверки

Полный безопасный сценарий (без выключения, выхода и сна):

```powershell
pwsh -File scripts\verify-windows.ps1
```

Он проверяет: регистрацию обхода на оконно-невидимый лаунчер (и GUI-подсистему лаунчера);
передачу кода выхода дочернего процесса и отказ лаунчеру в чужих командах; что `StartBoundary`
точной задачи не раньше `due` (включая дробные секунды); что Windows **сам** доставляет напоминание
по сроку, при этом у процессов лаунчера и дочернего exe не наблюдается видимых окон; что задача
убирается после доставки; что миграция legacy-задачи (`Command` = консольный exe) переводит её на
лаунчер с сохранением `StartBoundary` и интерактивного контекста; что обход продолжает миграцию,
если установка её не закончила; что сборка без лаунчера честно предупреждает; что отключённый
точный триггер догоняется обходом; что тестовые записи удалены. Скрипт печатает `PASS/FAIL` по
каждому пункту и**не очищает** общую историю уведомлений.

Прогон на отдельной сборке в изолированном окружении (не трогает live-задачи и данные):

```powershell
$staging = "$env:TEMP\opencode\agentnotify-staging"
pwsh -File scripts\build.ps1 -Target $staging
$env:AGENTNOTIFY_HOME = "$env:TEMP\opencode\agentnotify-home"
pwsh -File scripts\verify-windows.ps1 -Exe "$staging\AgentNotify.exe"
& "$staging\AgentNotify.exe" uninstall    # убрать только свои тестовые задачи
Remove-Item Env:AGENTNOTIFY_HOME
```

Пошагово:

```powershell
$exe = "$env:LOCALAPPDATA\AgentNotification\app\AgentNotify.exe"
& $exe test-toast --text "Проверка toast"
& $exe schedule --at ((Get-Date).AddMinutes(2).ToString("yyyy-MM-ddTHH:mm:sszzz")) --text "Проверка срока"
& $exe list --json
& schtasks /Query /TN "<windowsTaskName из вывода schedule>" /V /FO LIST
& $exe cancel <id>
```

Что этим не проверяется и требует человека: показ баннера при **закрытом OpenCode** (можно
проверить, закрыв OpenCode после постановки напоминания), доставка после **реального выхода и
входа** в Windows, после **сна** без перелогина, видимость баннера при включённом «Не беспокоить»,
и субъективное отсутствие мелькания окна (скрипт объективно подтверждает GUI-подсистему лаунчера,
запуск дочернего процесса без окна и отсутствие видимых окон у наблюдаемых процессов доставки,
но «пользователь не увидел вспышку» проверяет только человек).
